# Iris time services — 2026-09-22

Flashed the verified `build/iris-0.3.0` images through the CH340 UART port.
Esptool identified ESP32-S3 revision 0.2, MAC `30:ed:a0:0c:7e:98`, and verified
all written image hashes.

Live results:

- BLE `PING` passed; `INFO` reported firmware `0.3.0`, protocol 1, VM 1.
- Direct `TIME_NOW` returned monotonic millisecond values with `wrap_bits=32`.
- Loaded `programs/time_now.hex` over BLE: 6 bytes, execution halted at PC 6,
  and register 0 contained the sampled monotonic time.
- UART `CAPS` reported `TIME_MONOTONIC` and `1:TIME_NOW`.
- A final BLE `PING` passed after VM execution.

Known host/transport issue: the full `CAPS` response succeeds over UART but the
current BLE reply path cannot carry or assemble that long frame; `irisctl caps`
times out. Short BLE request/reply commands, including VM control and
`TIME_NOW`, work normally.

## TIME_RESET and shared runtime follow-up

The runtime moved from its former Iris-local directory to `esp/common`;
portable arithmetic and time programs moved to `esp/common/programs`. Iris now
compiles her physical definition directly against that shared library.

Firmware `0.3.1` adds common syscall `2:TIME_RESET`. Live BLE results were
`30400 -> reset=0 -> 550 -> 2150` ms. The portable six-byte `time_reset` VM
halted at PC 6 with r0=0; `TIME_NOW` read 1250 ms afterward, and the portable
`time_now` VM later halted with r0=2500. Unsigned subtraction keeps the logical
clock correct across the underlying 32-bit hardware timer wrap.

The Iris-specific `police_lights` VM was also loaded over BLE. It remained in
`WAITING` while alternating GPIO17 blue and GPIO47 red every 125 ms, then
`police-stop` stopped the VM, forced both outputs low, and a final PING passed.
