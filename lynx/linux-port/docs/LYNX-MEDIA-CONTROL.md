# Lynx media control

Lynx now has a local media service, `lynx-media`, for sounds and portrait
images. It has independent queues for sound and image, with `play`, `pause`,
`resume`, `stop`, `queue`, `next`, `previous`, `clear`, `status`, and
`catalog` commands. The server listens on the root-only Unix socket
`/run/lynx/media.sock`. Nexus uses pinned Alpine SSH on port 2222; no new
network listener is exposed.

The sound catalog is JSON at `/var/lib/lynx-media/catalog.json`. The initial
entries are `beep`, `double_beep`, and `chime`. The first is the verified
700 Hz half-second test. The other two are generated by
`tools/make_lynx_sounds.py` and stored under `sounds/` on Nexus and
`/var/lib/lynx-media/sounds/` on Lynx. The controller rereads the catalog
for each request, so adding an entry does not require restarting the service.
New WAVs must be stereo, 16-bit, 48 kHz, at most 30 seconds and 3 MB, with a
peak below 10% of full digital scale. This conservative limit stays in place
until the analog volume path is characterized.

From Nexus:

```sh
cd /noobia/lynx
python3 tools/lynx_media_remote.py catalog
python3 tools/lynx_media_remote.py play sound chime
python3 tools/lynx_media_remote.py queue sound double_beep
python3 tools/lynx_media_remote.py pause sound
python3 tools/lynx_media_remote.py resume sound
python3 tools/lynx_media_remote.py next sound
python3 tools/lynx_media_remote.py previous sound
python3 tools/lynx_media_remote.py stop sound
python3 tools/lynx_media_remote.py status
```

For portraits, use the same commands with `image` and a pose or animation
name, such as `01_standing_smile` or `dance`. The full image catalog comes
from `/var/lib/lynx-display/frames/manifest.json`, including poses added
later by `lynx-displayctl`. A queued pose displays for five seconds before
advancing. A queued animation displays one cycle at its manifest frame rate.
When the queue ends, the last image stays on screen. Pausing an animation
freezes its displayed frame; resuming restarts that animation's cycle. The
existing direct `lynx-displayctl` remains available, but using it while a
media image queue is playing can cause the two controls to overwrite each
other's selection.

`play` starts a named item now. `queue` appends it and starts it if the
channel is idle. `next` skips to the next queued item; `previous` starts
the most recently played item. `stop` stops playback and clears that
channel's queue. Both queues and history are stored in
`/var/lib/lynx-media/state.json`; after a service restart they remain
available but playback starts stopped. Speaker route controls are restored
and both amplifiers are muted after playback, stop, or service exit.

The media service is enabled in Alpine's default OpenRC runlevel. Its first
audio trials loaded the corrected MT6338 module and matching TFA98xx firmware
into RAM separately. The automatic audio bootstrap added later is described
below. No boot partition was changed for these services.

## Remote control check after reboot

On V50 boot `42256da1-930e-4469-9370-cfba5ff1fd93`, the audio card was
initially absent. With Lynx charging, a one-time 25% battery floor was
requested for the two RAM-only audio probes using
`LYNX_AUDIO_MIN_BATTERY_PERCENT=25`; the normal default remains 50%.
The probes require positive charging current whenever this override is below
50%, and reject thresholds below 25%. The matching MT6338 providers and
corrected sound card loaded, then the already installed matching TFA98xx
firmware was selected and loaded with both speakers muted. Module receipts:
`logs/v50-audio-provider-1793195496473276444/` and
`logs/v50-audio-card-1793195506917057440/`.

From Nexus, NRP/1 returned success for `CALL_MIXED IMAGE_POSE
"05_using_device"`, `CALL_MIXED SOUND_PLAY "beep"`, and `CALL HAPTIC_SET 80 1`.
The media queue recorded the beep; afterward both speaker mute controls were
`On`, haptic status was inactive, and `lynx-status --assert-ready` reported
no issues at 36% battery and 28.7°C battery temperature. Actual audibility
of this beep requires confirmation from a person near Lynx. At that point the
audio modules were RAM-only; automatic loading was added in the next step.

## Automatic sound startup

The matching module plan, corrected MT6338 codec, and TFA98xx firmware are now
stored under `/var/lib/lynx-audio/v1` on Alpine. `lynx-audio` is enabled in
the default OpenRC runlevel and loads the card after `lynx-display`, checks
each module hash, waits for ALSA card registration, and keeps both speakers
muted after firmware initialization. Its log is
`/var/log/lynx-audio-bootstrap.log`. No boot partition was changed.

The first cold boot needed a manual audio service start, so its receipt was
corrected to `verified-after-manual-audio-start`:
`logs/v50-audio-cold-boot-1793197983022386992/`. On the second clean boot,
`lynx-display` stopped partway through its module list, leaving haptics and
audio stopped. That failed check is
`logs/v50-audio-cold-boot-1793198366206634557/`. The display module loader's
per-module guard now checks battery, thermal, and filesystem integrity; the
full Alpine health guard still runs before and after display startup.

The next clean boot passed **without manual intervention**:
`logs/v50-audio-cold-boot-1793198926121333822/`. Display, haptics, media,
Noob runtime, and audio services were all running. NRP/1 `AUDIO_READY`
returned `card=1 firmware=1`, `HAPTIC_STATUS` returned inactive, and
`lynx-status --assert-ready` reported no issues at 51% battery and 29.5°C
battery temperature. This verifies automatic sound readiness; it does not
request audible playback at boot.
