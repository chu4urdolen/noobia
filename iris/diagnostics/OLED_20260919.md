# OLED on GPIO17/18 — 2026-09-19

User reports OLED on GPIO17/18, remaining external LEDs on GPIO15/40.
Firmware assumes OLED SDA=17 and SCL=18. Physical wire order and voltage at
the OLED connector have not been independently measured this session.

## Firmware and isolation

- Built and flashed `0.2.8-i2c-17-18`, 1,363,343 bytes of application code.
- Build: `/noobia/iris/build/iris-i2c-17-18-20260919`.
- Flash completed with hash verification; no NVS or SD erase was requested.
- OLED drawing/soft-I2C code remains excluded. External hardware I2C stays
  dormant until a native `I2C_CONFIG` command.
- Iris owns the pin assignments; reusable I2C code owns transactions.
- Remaining LED channels are 0=GPIO15 and 2=GPIO40. Removed channels 1/3
  are rejected. LED calls no longer close I2C or use I2C pin constants.
- Native `I2C_SCAN [first [last]]` accepts addresses 8..119 and distinguishes
  ACKs, NACKs, timeouts, and other failures. No GPIO sweep was performed.

## Observations over BLE

1. `INFO` confirmed the new firmware. Configuring SDA17/SCL18 at 100000 Hz
   succeeded. Both input levels read high with the controller started.
2. Probing only 0x3C and 0x3D returned `ack=0 nack=2 timeout=0 other=0`,
   elapsed 504 us for the two probes. After close, both levels remained high.
   `PING` returned `PONG`.
3. Repeating after requesting 10000 Hz returned the same counters in 510 us.
   **This was not a real slower probe.** The installed Arduino core delegates
   zero-length writes to ESP-IDF `i2c_master_probe`, which explicitly sets
   100000 Hz independently of the configured device frequency.
4. A separate test configured 10000 Hz and attempted a normal data write to
   0x3C with bytes `00 AE` (command-control, SH1107 display off). Unlike the
   probe, this path uses the configured device speed. The reply was
   `ERR NATIVE_ERROR I2C write error code=4`. This is a generic Wire error;
   the reply does not identify the underlying ESP-IDF error or failing byte.
   The script stopped immediately, so its planned 0x3D write was NOT sent.
5. Cleanup returned `closed pins_released=1`; a final BLE ping returned PONG.

No initialization sequence or display-RAM data was sent. No LED commands,
camera tests, broad address scans, bit-banging, or timing sweeps were run.
GPIO input-high readings do not prove a healthy waveform, correct connector
wiring, or adequate OLED supply voltage. These tests do not prove a bad OLED.

## Driver reference and follow-up

Installed core: Arduino-ESP32 3.3.11, ESP-IDF 5.5.5. Local
`esp32-hal-i2c-ng.c:i2cWrite` uses `i2c_master_probe` for zero-length writes;
nonempty writes use a device handle with the configured `scl_speed_hz`.
Espressif's [ESP-IDF 5.5.5 source](https://github.com/espressif/esp-idf/blob/v5.5.5/components/esp_driver_i2c/i2c_master.c#L1264)
confirms the fixed probe clock.

Next physical check: DC voltage directly between the OLED's own GND and VCC
pins while powered, without changing wiring. Next software diagnostic worth
adding: expose the underlying ESP-IDF error name and actual probe frequency,
so generic Wire errors and requested clock settings cannot mislead us.
