# Lynx hardware tools: local and NRP/1

Implemented 2026-10-29 as the first shared interface for Lynx's microphone,
flashlight, GNSS, Bluetooth, and camera. The same read-only inventory powers
`/usr/local/bin/lynx-hardware status <device|all>` on Lynx and five NRP/1
native calls from Nexus:

| NRP/1 ID | Call | Local JSON-stdin wrapper |
| --- | --- | --- |
| 390 | `MIC_STATUS` | `lynx_microphone.sh` |
| 391 | `FLASH_STATUS` | `lynx_flashlight.sh` |
| 392 | `GNSS_STATUS` | `lynx_gnss.sh` |
| 393 | `BT_STATUS` | `lynx_bluetooth.sh` |
| 394 | `CAMERA_STATUS` | `lynx_camera.sh` |
| 395 | `MIC_LEVEL` | `lynx_microphone_level.sh` |

The local wrappers and adjacent `.json` schemas live in
`/usr/local/share/lynx-tools/calls/` on Lynx; source is in
`lynx/tools/local_calls/`. Each accepts `{}` on stdin and returns JSON. This
follows Rose's agent wrapper pattern. The NRP/1 calls use Iris's common native
call shape and return `value=0` until a function has actually been validated;
their detail includes `interface_ready` separately. A device node or loaded
module alone never sets `validated=1`.

`MIC_LEVEL` is the first bounded action. It uses the already tested ALSA
input route for exactly one second, reports late-window RMS and peak, and
discards the PCM in memory. The route refuses an unexpected mixer baseline,
checks Alpine, battery, and thermal health, and restores the two changed
controls in a `finally` path. There is no background listener or saved audio.
The local script is `lynx/tools/lynx_microphone_level.py`, also installed as
`/usr/local/bin/lynx-mic-level`. It currently needs an account with access to
the ALSA controls and the private capture lock; the future on-device AI's
account and local authorization boundary still need to be defined. NRP/1
remains restricted to Nexus. A level value alone does not prove that an external
sound reached the microphone; the separate clap trial below does.

The inventory reports a microphone ALSA capture interface. An external clap
validated acoustic response on the tested boot. The flashlight I²C chip is present but no driver
is bound; the earlier core unload hang still blocks another trial. GNSS now
has receiver nodes after the RAM-only module trial below, but no measured fix.
`/dev/ccci_c2k_agps` is a modem assistance node and is excluded. Bluetooth
has no HCI interface; camera has no video or media node.
The GNSS module also advertises `gps_nd*`, `gps_da*`, and `gps_mb*` nodes; the
backend recognizes them only with the actual GPS driver loaded. A second
read-only status correction is recorded in
`logs/v50-gnss-node-status-1793303826954647541.json`.

The backend is `lynx/tools/lynx_hardware.py`. The NRP/1 registration is in
`lynx/tools/lynx_noob_runtime.py`. `tools/install_v50_hardware_status.py`
installed both with a service rollback copy at
`/usr/local/bin/lynx-noobd.before-hardware-status`; the corrected GNSS node
check has another copy at `.before-hardware-status-gnss-fix` and backs up the
backend as `lynx_hardware.py.before-gnss-fix`. Receipts:
`logs/v50-hardware-status-1793303183328412852/result.json` and
`logs/v50-hardware-status-gnss-fix-1793303236954761983/result.json`.
The five live NRP/1 calls, local inventory, service restart, and Alpine health
passed. No boot partition or kernel module changed.

The microphone level tool was installed with a separate rollback copy in
`logs/v50-microphone-level-1793303657503077153/result.json`. A local one-second
sample returned late RMS 3.49 and peak 8; the NRP/1 `MIC_LEVEL` call returned
RMS × 100 of 322 and peak 10. Both reported no retained audio, and the mixer
restoration and post-install health checks passed. These are quiet ambient
readings; the later external clap supplied acoustic validation.
The local JSON tool's bounded input and error handling were verified in
`logs/v50-hardware-tool-error-fix-1793303764810765281.json`.

An offline `modinfo` dependency graph from the matching August package is
generated by `tools/analyze_v50_module_dependencies.py`. Its current receipt
is `logs/hardware-dependencies-1793303434757393031.json`: all 72 modules
reached from the four driver stacks match the V50 kernel version, and no
dependency name was missing from the package. A read-only comparison with
Lynx's loaded modules is in
`logs/hardware-live-gap-1793304049573421464.json`. It found four GNSS, two
Bluetooth, five camera, and three flashlight modules absent on that boot.
The graph gives dependency order, but does not establish probe safety or a
working userspace path. In particular, it does not clear the flashlight
unload hang or make the large camera stack safe to load unattended.
Read-only inspection of `bt_drv_6983.ko` found calls to
`hci_alloc_dev` and `hci_register_dev`. Both matching modules loaded in RAM
on V50, one at a time, with a 90-second reboot fallback. `/dev/stpbt` appeared
and Wi-Fi and Alpine stayed healthy, but no `hci*` interface appeared. The
driver log says `fwp_has_flavor_bin: get flavor_bin: fail`. Vendor transport
and firmware initialization remain to be worked out. Receipts:
`logs/v50-bluetooth-btif_drv-1793305632764445738/result.json` and
`logs/v50-bluetooth-bt_drv_6983-1793305649275022156/result.json`.

Next, add bounded actions only after their hardware paths pass the separate
trials in [LYNX-REMAINING-HARDWARE-TRIALS.md](LYNX-REMAINING-HARDWARE-TRIALS.md).
The microphone passed its external sound response test; the other four need
driver and userspace work first. Local tools should call the same validated
backend as NRP/1 so Lynx's future on-device agent and remote controllers see
the same safety state.

Three quiet one-second microphone levels were captured, with a median RMS ×
100 of 499, in `logs/v50-microphone-quiet-1793305060934251199.json`.
The user confirmed a clap on the same boot; RMS × 100 reached 5888 (11.8×
the quiet median) and peak 1164. No raw audio was saved; controls were
restored and health passed. Receipt:
`logs/v50-microphone-clap-1793305372427637018.json`. The 14 initially absent stock
driver modules were hash-verified and staged under
`/run/lynx-hardware-modules/` without loading them; receipt:
`logs/v50-hardware-modules-staged-1793305118730077737.json`.

## Live GNSS dependency trial

On 2026-10-29, the four matching GNSS modules were loaded into V50 RAM in
order, with an independent 90-second reboot fallback per module. `connscp`,
`gps_scp`, `gps_pwr`, and `gps_drv_dl_v050` all returned successfully; Wi-Fi,
SSH, and Alpine health remained intact. Lynx exposed `/dev/gpsdl0`,
`/dev/gpsdl1`, `/dev/gps2scp`, and `/dev/gps_pwr`. No receiver was powered on
and no position fix was attempted. Receipts:

- `logs/v50-gnss-connscp-1793305750852527719/result.json`
- `logs/v50-gnss-gps_scp-1793305764769019303/result.json`
- `logs/v50-gnss-gps_pwr-1793305779405195317/result.json`
- `logs/v50-gnss-gps_drv_dl_v050-1793305794479539205/result.json`

The installed local and NRP/1 inventory now recognizes `gpsdl*` as receiver
nodes. It reports the microphone as validated by the user-confirmed external
clap, GNSS as interface-ready but unvalidated, and Bluetooth as driver-loaded
without an HCI interface. The update restarted only `lynx-noobd`, retained a
rollback copy, and passed live health and service checks. Receipt:
`logs/v50-hardware-trial-status-1793305854986125810.json`.

After the timed V50 GNSS and Bluetooth open probes, a shared MediaTek radio
calibration stall was traced and cleared by a normal reboot. V52's changed
load order resolved calibration. Nexus discovered Lynx's BLE advertisement;
GNSS powered on and opened its data link, but no position was measured.
Diagnostics and exact rollback are recorded in
[LYNX-CONNECTIVITY-PRECAL.md](LYNX-CONNECTIVITY-PRECAL.md).
