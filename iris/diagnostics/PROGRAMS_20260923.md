# Noob program architecture — 2026-09-23

Built and flashed Iris firmware 0.4.0 through CH340 USB. Esptool identified the
ESP32-S3 at MAC `30:ed:a0:0c:7e:98` and verified every flash region.

## Verified

- Compiled two-channel `POLICE_SEQUENCE` started with both positions at 0/10.
  After 2.5 seconds it stopped at 10/10, with 10 integers in each channel queue
  and zero drops.
- `police_sequence_vm.hex` loaded 81 bytes, halted at PC 81, and configured
  the same two channels from VM registers. Both again reached 10/10 with 10
  queued results each.
- `ultrasonic_change_start.hex` loaded 20 bytes and started the thread with a
  100 mm threshold and 250 ms interval. Status reported running; the dedicated
  stopper returned it to stopped. A direct distance read afterward returned
  58 mm from three echoes.
- Final busy-enabled firmware reported `channel_busy=0,0,0,0` between calls,
  `SEQUENCE_BUSY 0=0`, `SEQUENCE_BUSY 1=0`, completed both LED channels,
  and answered PING.

The initial delayed-input test used `sg dialout -c`, which buffered the input
pipe before launching the client. A persistent direct serial session showed
the correct timing. The false stall report is retained here so this diagnostic
trap is not rediscovered.

An attempted FreeRTOS worker for synchronous GATT connection caused Iris to
reboot because the legacy BLE client was touched across tasks. That worker was
removed. BLE scanning remains asynchronous; connection uses the library's
supported context and bounded retry interval.

## Motion-to-police VM

Built, flashed, and hash-verified firmware 0.4.2. The final native police
sequence uses ten alternating 200 ms states and an explicit final zero on both
channels. Hardware results reached 11/11; both GPIO17 and GPIO47 queues ended
in zero with no drops.

The ultrasonic detector samples every 250 ms with a 100 mm threshold. At rest,
12 measurements stayed within 1244..1249 mm. After an event it rearms only
after four stable samples, so continuous motion does not flood timestamps.
Events contain logical monotonic time only.

`police_on_ultrasonic_change.hex` loaded 63 bytes. A physical hand movement
started the full two-second police sequence. After completion:

- VM remained waiting for the next event;
- ultrasonic queue was empty with zero drops;
- both sequence positions were 11/11;
- both LEDs were off.

An earlier 54-byte draft used common ID 5 as status. ID 5 is
`SEQUENCE_STOP`, so that draft stopped after the first blue state. The final
VM correctly calls `SEQUENCE_STATUS` as common ID 6 and drains timestamps
accumulated while the lights are busy.
## Dynamic light and sequence-busy verification — firmware 0.4.6

The reusable change thread established a live GPIO1 baseline near 7 counts.
Direct LED testing previously measured about 372 counts with both external LEDs
on, so the configured 200-count delta is physically meaningful.

Sequence activity is now represented at both layers: low-level native invocation
busy remains transient, while thread and sequence `channel_busy` covers the full
higher-level execution. During a finite police run, status at position 3/11 was
`running=1 channel_busy=1,1,0,0`; the light detector simultaneously reported
`running=1 channel_busy=1 queued=0`. After 11/11, the sequence bits were zero,
the detector was still running, and `LIGHT_CHANGE_POLL` returned `event=0`.
Thus photoresistor sampling was suppressed for the LED run and resumed with a
fresh baseline rather than detecting the police lights.

The corrected 85-byte `police_on_sensor_change` VM starts both detector threads,
triggers police from either event queue, and waits for sequence completion. It no
longer stops or restarts light detection. It was loaded, run over BLE, and saved
to `/programs/police_on_sensor_change.nvm` on the SD card.
